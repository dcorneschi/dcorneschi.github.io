# LD_LIBRARY_PATH and Shared Libraries

How the dynamic linker finds shared libraries, when to use `LD_LIBRARY_PATH`, compiling software in `$HOME`, and managing system library paths with `ldconfig`.

## How the Dynamic Linker Works

When an application starts, the dynamic link loader (`ld.so`) searches for shared libraries in this order:

1. Paths in `LD_LIBRARY_PATH` (if set)
2. Paths compiled into the binary (`RPATH`/`RUNPATH`)
3. Paths cached in `/etc/ld.so.cache` (generated by `ldconfig`)
4. Standard locations (`/lib`, `/usr/lib`, `/lib64`, `/usr/lib64`)

## LD_LIBRARY_PATH

`LD_LIBRARY_PATH` tells the dynamic linker where to search for shared libraries before the compiled-in paths and standard locations. Multiple directories are separated by colons (`:`).

### Valid Use Cases

- Testing new versions of a shared library against an already compiled application
- Relocating shared libraries (e.g., preserving old versions)
- Creating self-contained, relocatable environments for applications that shouldn't depend on system libraries

### Security Implications

- Directories in `LD_LIBRARY_PATH` are searched **before** standard locations — a malicious library placed there could be loaded instead of the real one
- `setuid`/`setgid` executables ignore `LD_LIBRARY_PATH` for this reason

### Performance Implications

- The linker searches all listed directories for **every** shared library the application needs
- Each lookup issues `open()` syscalls that fail with `ENOENT` until the library is found
- More directories = linearly slower startup, especially on NFS

### Inconsistency Risks

- Forcing an application to load a library it wasn't linked against can cause crashes or subtle wrong results
- Debugging incorrect library versions is particularly difficult when results are silently wrong

## Best Practices

1. **Never set `LD_LIBRARY_PATH` globally** in login profiles or system-wide
2. **Never include system library paths** — those are handled by `ldconfig`
3. **Set it per-application** on the command line, immediately before execution
4. **Keep it isolated** — don't let it leak into other processes

### Correct Usage

```bash
# Set only for this one command
LD_LIBRARY_PATH=/path/to/lib1:/path/to/lib2 ./myprog

# Or in a wrapper script
#!/bin/sh
LD_LIBRARY_PATH=/path/to/lib1:/path/to/lib2:/path/to/lib3
export LD_LIBRARY_PATH
exec /path/to/bin/myprog "$@"
```

### Wrong Usage

```bash
# DON'T put this in .bashrc or .profile
export LD_LIBRARY_PATH=/path/to/lib1:/path/to/lib2:/path/to/lib3
./myprog
```

### Testing from the Command Line

```bash
env LD_LIBRARY_PATH=/path/to/lib1:/path/to/lib2 ./myprog
```

## Inspecting Shared Libraries

```bash
# Show shared libraries an application needs
ldd /usr/bin/file

# Show only missing libraries
ldd /usr/bin/file | grep "not found"

# Show the search path the linker uses
LD_DEBUG=libs ./myprog 2>&1 | head -50
```

## Diagnosing LD_LIBRARY_PATH Problems

If an application crashes or behaves unexpectedly, test whether `LD_LIBRARY_PATH` is the cause by stripping the environment:

```bash
# Run with a clean environment (no inherited variables)
env -i /some/command
```

If `/some/command` breaks normally but works with `env -i`, the problem is in your environment — `LD_LIBRARY_PATH` is the most common culprit.

```bash
# Confirm by running with only LD_LIBRARY_PATH removed
unset LD_LIBRARY_PATH && /some/command

# Or explicitly test with the suspected path
env LD_LIBRARY_PATH=/suspected/path /some/command
```

## Adding System Library Paths with ldconfig

The system-wide library search path is defined in `/etc/ld.so.conf` and `/etc/ld.so.conf.d/`. The linker reads the pre-compiled cache at `/etc/ld.so.cache` for fast lookups.

### Add a New Library Path

```bash
touch /etc/ld.so.conf.d/mylib.conf
echo "/path/to/lib" > /etc/ld.so.conf.d/mylib.conf
ldconfig
```

### Verify

```bash
# Check if a library is in the cache
ldconfig -p | grep libfoo

# Rebuild the cache
ldconfig

# Show all cached libraries
ldconfig -p
```

> **Warning:** Do not add paths to `ld.so.conf` that contain libraries overriding system libraries — this can cause system instability.

## Compiling in $HOME

When you don't have root access or want to install software locally:

### Configure with Home Prefix

```bash
./configure --prefix=$HOME
make
make install
```

### With Local Library Dependencies

```bash
./configure --prefix=$HOME --with-foolib=$HOME/lib
```

### When ./configure Doesn't Support Custom Paths

Pass compiler and linker flags directly:

```bash
CFLAGS="-I$HOME/include" LDFLAGS="-L$HOME/lib" ./configure --prefix=$HOME
```

### Environment Setup for Home Installs

Add to `~/.bashrc`:

```bash
export LD_LIBRARY_PATH=$HOME/lib
export PATH="$HOME/bin:$PATH"
```

> **Note:** Setting `LD_LIBRARY_PATH` in `.bashrc` is acceptable for user-local installs in `$HOME` where system libraries are not overridden. Avoid including system paths.

## Summary

| Scenario | Approach |
|----------|----------|
| System-wide library path | Add to `/etc/ld.so.conf.d/` and run `ldconfig` |
| Per-application override | Prefix command with `LD_LIBRARY_PATH=...` |
| Wrapper script | Set and export `LD_LIBRARY_PATH`, then `exec` the binary |
| Compiling locally | `./configure --prefix=$HOME` + `LD_LIBRARY_PATH=$HOME/lib` |
| Testing a new library version | `LD_LIBRARY_PATH=/path/to/new/lib ./myprog` |
| Production servers | Use `ldconfig`, avoid `LD_LIBRARY_PATH` globally |
